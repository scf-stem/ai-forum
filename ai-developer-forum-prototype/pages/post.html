LangChain RAG 检索结果召回率低，如何优化向量存储与重排序？

林 林炜 @linwei · 前端工程师 2 天前 1,248 次浏览

最近在用 LangChain 搭建一个内部知识库问答系统，数据源是几百份 Markdown 技术文档。整体流程是：文档切分 → OpenAI text-embedding-3-small 向量化 → 存入 Chroma → 检索时用 similarity_search 取 Top 5 → 直接交给 GPT-4 生成答案。

目前遇到两个比较头疼的问题：

  1. 用户问一些跨段落、需要综合多份文档的问题时，Top 5 经常召回不全，导致答案漏掉关键约束。
  2. 有些查询明明关键词匹配度很高，但向量相似度排名把真正相关的片段挤到了后面。

我已经尝试过调整 chunk_size（512 / 1024 / 2048）和 overlap（50 / 100 / 200），效果都不太稳定。想请教 community 里做过生产级 RAG 的同学，除了换 embedding 模型，还有哪些行之有效的优化路径？

另外，我也在考虑引入重排序（reranker），比如 Cohere Rerank 或 bge-reranker-large，但不确定在 LangChain 里怎么和现有的检索链整合最优雅。如果有完整的代码示例或踩坑经验，非常感谢！

AI 结构化答案

基于社区高赞回答与官方文档综合生成

高置信度

针对你的 RAG 召回问题，建议从「检索策略」和「结果精排」两个层面同时优化，而不是只调整 chunk 参数。

1. 检索策略升级

  • 混合检索（Hybrid Search）：向量相似度对关键词精确匹配不够敏感，可叠加 BM25/TF-IDF 关键词检索，再用 Reciprocal Rank Fusion（RRF）合并两个榜单。
  • 查询扩展（Query Expansion）：让 LLM 先把用户问题改写为 2-3 个同义查询，分别检索后合并结果，可显著缓解语义漂移。
  • 父文档检索（Parent Document Retrieval）：小块用于匹配，返回时把完整父文档段落一起送入 LLM，兼顾定位精度与上下文完整。

2. 重排序接入

在 LangChain 中，最简洁的做法是使用 ContextualCompressionRetriever 包装基础检索器，再传入一个基于 Cohere 或 Hugging Face 的 compressor。

python 
from langchain.retrievers import ContextualCompressionRetriever
from langchain_cohere import CohereRerank

compressor = CohereRerank(top_n=5)
compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=retriever
)

3. 关键指标建议

Top 5 → Top 10 召回后再精排
RRF k=60 混合检索融合参数
rerank top_n=5 最终送入 LLM

    生产环境里我们最管用的三招：① 把默认的 similarity_search 换成 MMR，提升多样性；② 引入 Cohere Rerank，把 20 个候选压到 5 个；③ 对文档做层次切分，父块 1024 token、子块 256 token，检索时命中子块、返回父块。

    另外，建议把查询也做向量化前先做一次 HyDE：让 LLM 根据问题生成一个假设答案，再用假设答案去做向量检索，对开放性问题召回率提升很明显。
